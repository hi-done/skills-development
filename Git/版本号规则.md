# 语义化版本号（Semantic Versioning / SemVer）

版本号格式就三坨数字，用点隔开：

```
MAJOR.MINOR.PATCH
 2  .  1  .  3
```

---

## 每个位置的含义

| 位置   | 名字      | 什么时候 +1                 | 一句话理解                        |
| ------ | --------- | --------------------------- | --------------------------------- |
| 第一位 | **MAJOR** | 做了**不兼容的 API 变更**   | 升了它 = 用户升级要改代码         |
| 第二位 | **MINOR** | 加了**向下兼容的新功能**    | 升了它 = 有新东西，但老代码不用动 |
| 第三位 | **PATCH** | 做了**向下兼容的 bug 修复** | 升了它 = 修 bug，啥都不用改       |

> 核心原则：**只看"对用户有没有破坏性"**，不看你改了多少行代码。改了 500 行但没破坏接口 → PATCH；只改了 1 行但删了个公开 API → MAJOR。

---

## 用现实例子理解

假设你做了个 npm 包，当前版本 `1.4.2`：

| 你做的事                         | 新版本  | 为什么                     |
| -------------------------------- | ------- | -------------------------- |
| 修了一个计算错误                 | `1.4.3` | PATCH — bugfix             |
| 加了个 `formatDate()` 新函数     | `1.5.0` | MINOR — 新功能，不影响老的 |
| 把 `formatDate()` 的参数顺序换了 | `2.0.0` | MAJOR — 老用户调用会报错   |
| 性能优化，结果没变快多少         | `1.5.1` | PATCH — 纯内部改进         |
| 性能优化，接口没变但快了 10 倍   | `1.6.0` | MINOR — 用户能感知到价值   |

---

## 版本号递增规则（关键）

**每次发版只动一个数字，它右边的全部归零：**

```
1.4.2
  │
  ├─ PATCH bump → 1.4.3
  │
  ├─ MINOR bump → 1.5.0  （PATCH 归零！）
  │
  └─ MAJOR bump → 2.0.0  （MINOR 和 PATCH 都归零！）
```

⚠️ 注意：**MINOR 升的时候 PATCH 归零，MAJOR 升的时候 MINOR 和 PATCH 都归零**。很多人会写成 `2.0.2` 这种，这是错的。

## 预发布版本（带横杠）

```
1.0.0-alpha
1.0.0-alpha.1
1.0.0-beta.2
1.0.0-rc.1
1.0.0
```

规则：
- 横杠后面是**预发布标识**，按 `.` 分隔比较优先级
- 预发布版本 **优先级低于正式版**：`1.0.0-beta < 1.0.0`
- 同一阶段内数字越大越新：`alpha.1 < alpha.2`

常见生命周期：`alpha`（内测）→ `beta`（公测）→ `rc`（发布候选）→ 正式版

---

## 版本号前面的 `v` 前缀

```bash
v1.2.3    # Git tag 里常见
1.2.3     # package.json / go.mod 里常见
```

`v` 只是**标签前缀**，不是版本号的一部分。SemVer 规范本身不带 `v`，但 Git 社区习惯加。工具一般都能识别两者。

---

## 和上一轮 Conventional Commits 的关系

这就是为什么要按 `feat` / `fix` / `BREAKING CHANGE` 分类 commit：

| Commit 类型       | 自动决定       |
| ----------------- | -------------- |
| `feat`            | MINOR +1       |
| `fix`             | PATCH +1       |
| `BREAKING CHANGE` | MAJOR +1       |
| 其他              | 不触发版本变化 |

工具（如 `semantic-release`）扫一遍 commit 历史，自动算出下一个版本号，全自动。

---

## 几个常见误区

| 误区                       | 真相                                             |
| -------------------------- | ------------------------------------------------ |
| "改了很多代码就该升 MAJOR" | ❌ 看兼容性，不看代码量                           |
| "MAJOR 到 1.0 才算正式"    | ❌ 0.x 也有规则（下面说）                         |
| "PATCH 只能修 bug"         | ❌ 文档 typo、内部重构、安全补丁都算 PATCH        |
| "版本号要跟功能数量挂钩"   | ❌ 一个功能也能升 MINOR，十个 bugfix 也只升 PATCH |

---

## 0.x 的特殊规则

版本号在 `1.0.0` 之前，SemVer 认为**"什么都可能在变"**：

| 版本              | 含义                                         |
| ----------------- | -------------------------------------------- |
| `0.1.0`           | 初始开发，MINOR 变 = 可能 breaking           |
| `0.1.1` → `0.1.2` | 还是 PATCH（修 bug）                         |
| `0.2.0`           | 加了功能，但**不保证兼容**                   |
| `1.0.0`           | 正式承诺：公共 API 稳定，之后严格遵循 SemVer |

所以很多库在 `0.x` 阶段随便改 API 不升 MAJOR——这是**允许的**，因为还没到 1.0 就不算破坏承诺。

---

## 一句话总结

> **MAJOR = 升了要改代码；MINOR = 升了有新东西但不用改；PATCH = 升了只是修 bug。右边归零，左边不动。**

## 常见的版本后缀大全

按"成熟度从低到高"排：

| 后缀                | 全称              | 含义                                 | 典型场景                           |
| ------------------- | ----------------- | ------------------------------------ | ---------------------------------- |
| `-SNAPSHOT`         | snapshot          | 开发中的快照，**随时在变**           | Maven/Java 生态天天见              |
| `-dev`              | development       | 开发版，不稳定                       | 内部日常构建                       |
| `-alpha` / `-a`     | alpha             | 内测版，**功能不完整，bug 多**       | 给核心开发者/内部人测              |
| `-beta` / `-b`      | beta              | 公测版，**功能基本齐了，可能有 bug** | 公开邀请用户测                     |
| `-rc`               | Release Candidate | 发布候选，**觉得稳了，最后验证一轮** | 正式发版前的最后一道关             |
| `-preview`          | preview           | 预览版，非正式                       | 让你提前看看新功能长啥样           |
| `-m` / `-milestone` | milestone         | 里程碑版                             | 阶段性成果，不一定稳定             |
| `-sp` / `-patch`    | service pack      | 补丁包                               | Windows / 企业软件常见             |
| `-pl`               | patch level       | 补丁级别                             | AIX / 某些 Unix 系统               |
| `-hotfix`           | hotfix            | 紧急修复版                           | 线上出事了直接出                   |
| `-stable`           | stable            | 稳定版标记                           | 跟 nightly 相对（Rust 用过）       |
| `-nightly`          | nightly           | 每日构建版                           | 自动每天凌晨拉代码编译             |
| `-canary`           | canary            | 金丝雀版（最早放出去探路）           | 浏览器/Infra 领域常见              |
| `-edge`             | edge              | 前沿版，最新代码                     | Docker / 浏览器渠道                |
| `-lts`              | Long Term Support | 长期支持版                           | 不是稳定性后缀，是**支持周期**标记 |

## SemVer 规范里怎么定义的

按照 **Semantic Versioning 2.0 官方规范**，横杠后面叫 **Pre-release identifier**：

```
1.2.3-alpha.1
1.2.3-beta.2
1.2.3-rc.1
```

规则：

| 规则                          | 说明                              |
| ----------------------------- | --------------------------------- |
| 用**连字符 `-`** 开头         | `1.2.3-rc.1` ✅ / `1.2.3.rc.1` ❌   |
| 用**点 `.`** 分隔段           | `rc.1` 比 `rc.2` 旧               |
| **纯数字段**按数字比          | `beta.2 < beta.10`                |
| **含字母段**按 ASCII 字符串比 | `alpha < beta`（字典序）          |
| **段数多的更大**              | `1.0.0-alpha.1 < 1.0.0-alpha.1.1` |
| **预发布 < 正式版**           | `1.0.0-rc.1 < 1.0.0`（永远）      |

## 排序实战（从小到大）

```
1.0.0-alpha
1.0.0-alpha.1
1.0.0-beta
1.0.0-beta.2
1.0.0-rc.1
1.0.0-rc.2
1.0.0          ← 正式版，最大
```

包管理器（npm / Go modules / pip）都认这个排序。比如：

```bash
npm install mylib@^1.0.0-rc.1
# 会匹配 1.0.0-rc.2，但不会匹配 1.0.0（正式版）
# 因为预发布版本不会自动升级到正式版，需要你显式指定
```

> ⚠️ 这个行为很多人不知道：**`^1.0.0-rc.1` 不会自动升到 `1.0.0`**，npm 认为正式版可能破坏预发布用户的预期。要升正式版得手动改依赖版本。

---

## Go Modules 里怎么用

Go 的 module 版本也遵循 SemVer，但**默认不拉取预发布版本**：

```bash
go get mylib@v1.2.0-rc.1   # 必须显式指定
go get mylib               # 只拉 v1.2.0（正式版），忽略所有 rc/beta
```

Go 的排序也是标准的：
```
v1.2.0-rc.1 < v1.2.0
```

## 一个典型项目的发布生命周期

```
v0.1.0-dev        ← 开发中
v0.1.0-alpha.1   ← 内测
v0.1.0-alpha.2
v0.1.0-beta.1    ← 公测
v0.1.0-beta.2
v0.1.0-rc.1      ← 发布候选
v0.1.0-rc.2      ← 修了个小问题
v0.1.0           ← 正式！🎉
v0.1.1           ← 后续 bugfix
```
