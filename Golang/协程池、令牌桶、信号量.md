# 协程池、令牌桶、信号量

在 Go 并发编程中，**协程池、令牌桶、信号量** 都是控制并发的手段，但它们的设计目标和适用场景有明显差异。下面从核心机制、异同对比、典型场景三个层面来梳理。

---

## 一、核心机制速览

### 1. 协程池（Goroutine Pool）

**本质**：预先创建一组固定数量的工作协程，任务提交到队列，由空闲 worker 取走执行。

```go
// 典型结构
type Pool struct {
    tasks chan func()
}

func NewPool(size int) *Pool {
    p := &Pool{tasks: make(chan func(), 100)}
    for i := 0; i < size; i++ {
        go p.worker()
    }
    return p
}

func (p *Pool) worker() {
    for task := range p.tasks {
        task()
    }
}
```

- **控制的是**：协程数量（资源复用）
- **核心能力**：限制并发 worker 数 + 任务排队 + 避免无限制创建 goroutine

---

### 2. 令牌桶（Token Bucket）

**本质**：以固定速率向桶中放入令牌，每次操作前必须取到一个令牌才能执行，否则阻塞或丢弃。

```go
import "golang.org/x/time/rate"

limiter := rate.NewLimiter(rate.Limit(10), 5) // 10 req/s, burst=5

func handle() {
    if err := limiter.Wait(context.Background()); err != nil {
        return
    }
    // do work
}
```

- **控制的是**：速率（Rate Limiting）
- **核心能力**：平滑限流 + 允许突发（burst）+ 时间维度控制

---

### 3. 信号量（Semaphore）

**本质**：维护一个计数器，acquire 减一，release 加一，归零时阻塞。

```go
import "golang.org/x/sync/semaphore"

sem := semaphore.NewWeighted(3) // 最大并发 3

func handle() {
    if err := sem.Acquire(context.Background(), 1); err != nil {
        return
    }
    defer sem.Release(1)
    // do work
}
```

- **控制的是**：并发数量（资源准入）
- **核心能力**：限制同时执行的协程数，逻辑简单，无任务队列

> Go 标准库中没有直接暴露信号量，常用 `golang.org/x/sync/semaphore` 或 `channel` 自己实现。

---

## 二、三者的核心差异对比

| 维度             | 协程池              | 令牌桶                   | 信号量                      |
| ---------------- | ------------------- | ------------------------ | --------------------------- |
| **控制目标**     | 协程数量 + 任务调度 | 请求速率（时间维度）     | 并发数量（准入维度）        |
| **是否有队列**   | ✅ 有任务队列        | ❌ 无（或仅当前请求等待） | ❌ 无（等待 acquire）        |
| **是否限制速率** | ❌ 不限制速率        | ✅ 核心能力               | ❌ 不限制速率                |
| **是否复用协程** | ✅ 复用              | ❌ 不管理协程             | ❌ 不管理协程                |
| **突发处理**     | 队列堆积            | ✅ 支持 burst             | 直接阻塞                    |
| **复杂度**       | 较高                | 低                       | 极低                        |
| **典型实现**     | ants、自研          | `x/time/rate`            | `x/sync/semaphore`、channel |

## 三、使用场景对比

### 协程池 —— 重任务调度场景

**适合**：任务量大、单个任务较重、需要控制资源总量

| 场景             | 说明                                            |
| ---------------- | ----------------------------------------------- |
| 批量数据处理     | 10 万个文件需要处理，但不能开 10 万个 goroutine |
| 后端 Worker 服务 | 消费 MQ 消息，控制消费并发度                    |
| 数据库连接池配套 | 控制同时执行 SQL 的协程数，防止打满连接池       |
| 爬虫并发控制     | 同时爬取页面，但限制 worker 数量                |

```go
// 爬虫场景：100 个 worker 同时爬取
pool := NewPool(100)
for _, url := range urls {
    u := url
    pool.Submit(func() {
        crawl(u)
    })
}
```

---

### 令牌桶 —— 限流场景

**适合**：需要控制单位时间内的请求量，保护下游服务

| 场景           | 说明                                          |
| -------------- | --------------------------------------------- |
| API 接口限流   | 每个用户 100 QPS                              |
| 调用第三方 API | 遵守对方速率限制（如 GitHub API 5000次/小时） |
| 防止雪崩       | 突发流量削峰填谷                              |
| 分布式系统入口 | 网关层限流                                    |

```go
// 调用第三方 API，限制 5 QPS，允许突发 2
limiter := rate.NewLimiter(5, 2)

for {
    limiter.Wait(ctx)
    callThirdPartyAPI()
}
```

---

### 信号量 —— 简单并发度控制

**适合**：逻辑简单、不需要任务排队、只是不想同时跑太多

| 场景               | 说明                           |
| ------------------ | ------------------------------ |
| 限制 HTTP 并发请求 | 同时最多发 10 个请求           |
| 控制文件并发读写   | 同时最多 3 个文件写入          |
| 保护共享资源       | 限制同时访问某个昂贵资源的数量 |
| 简单脚本并发控制   | 一次性任务，不需要完整协程池   |

```go
// 同时最多 5 个 goroutine 执行
sem := semaphore.NewWeighted(5)
var wg sync.WaitGroup

for i := 0; i < 20; i++ {
    wg.Add(1)
    go func(id int) {
        defer wg.Done()
        sem.Acquire(ctx, 1)
        defer sem.Release(1)
        doWork(id)
    }(i)
}
wg.Wait()
```

## 四、组合使用

实际项目中三者经常**组合使用**，各司其职：

```
                    ┌─ 令牌桶：入口限流（QPS 控制）
HTTP 请求 ──────────┤
                    └─ 协程池：任务调度（worker 复用）

协程池 worker 内部 ─── 信号量：限制对下游 DB 的并发连接数
```

**典型分层架构**：

| 层次   | 手段   | 作用                               |
| ------ | ------ | ---------------------------------- |
| 入口层 | 令牌桶 | 防止系统被流量冲垮                 |
| 调度层 | 协程池 | 控制 goroutine 总数，任务排队      |
| 资源层 | 信号量 | 限制对 DB/缓存/外部 API 的并发访问 |

---

## 五、选型决策树

```
需要控制什么？
├── 控制 QPS / 速率 ──────────→ 令牌桶
├── 控制 goroutine 总数 + 任务排队 → 协程池
├── 只限制同时执行数，逻辑简单 ─→ 信号量
└── 以上都要 ──────────────────→ 组合使用
```

## 六、常见误区

| 误区                | 正解                                                             |
| ------------------- | ---------------------------------------------------------------- |
| 用 channel 当令牌桶 | channel 只能限制并发数，无法控制速率，不是令牌桶                 |
| 协程池能限流        | 协程池只限制并发 worker 数，如果任务提交速率极高，队列会无限增长 |
| 信号量能排队任务    | 信号量只阻塞 acquire，不存储任务，任务由调用方自行管理           |
| 令牌桶能限制并发    | 令牌桶限制的是速率，如果任务执行时间很长，并发数仍然可能很高     |
