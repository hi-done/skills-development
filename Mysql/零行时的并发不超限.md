# 零行时的并发不超限问题

## 问题描述

MySQL 的 `address` 表存放用户的收货地址，每一条记录代表一个收货地址。开始时每个用户的记录数为 0，并规定每个用户地址同时存在的**上限为 20 条**。

考虑并发场景：当某个用户的地址记录数为 0 时，如何避免 20 个以上设备同时为该用户创建地址，导致超过上限？

## 方案一：MySQL 行锁 / 间隙锁（适合并发量不高的情况）

适合并发量不高的情况。适用条件：单表、物理删除。

### 核心实现

```sql
START TRANSACTION;

-- 1️⃣ 锁住该用户的所有地址行（0 条也能锁）
SELECT 1
FROM address
WHERE user_id = :user_id
FOR UPDATE;

-- 2️⃣ 判断数量
SELECT COUNT(*) INTO @cnt
FROM address
WHERE user_id = :user_id;

-- 3️⃣ 如果未满，插入
IF @cnt < 20 THEN
    INSERT INTO address (user_id, address)
    VALUES (:user_id, :address);
END IF;

COMMIT;
```

> 可以合并 1️⃣ 和 2️⃣：

```sql
SELECT COUNT(*)
INTO @cnt
FROM address
WHERE user_id = :user_id
FOR UPDATE;
```

### 为什么"0 行也能锁"？

在 **RR（可重复读）** 隔离级别下，这条语句能锁住该 user_id 对应的"地址空间"。即使当前 0 行，也会通过 **Gap / Next-Key Lock** 把"将来能插入该用户地址的位置"锁住，从而防止其他事务插入该用户的新地址。

但它锁的不是"该用户所有地址行"这个概念，而是 **user_id 索引上的扫描范围**。具体行为完全取决于 `user_id` 上有没有索引、是什么索引：

- **有索引时**：锁的是 `user_id` 索引上 `= :user_id` 这个等值点对应的 **next-key / gap 范围**，而不是应用层意义上的"该用户行集合"
- **0 行时**：没有 record 可锁，但 gap 锁依然生效，所以"该用户未来地址的插入路径"被封死
- **本质作用**：它防的是**幻读**（防止别的事务插入该用户新地址），并不是给你一个"用户地址行锁列表"

### 不同索引下的锁行为

#### 1. `user_id` 是非唯一普通索引（最常见）

在 RR 下执行 `SELECT ... FOR UPDATE WHERE user_id = :x`：

- 对该 user_id 在二级索引上的每条匹配记录加 **X record lock**
- 同时加 **X gap lock / next-key lock**，锁住该 user_id 值所在的区间
- 如果该 user_id **当前 0 行**：扫描落到相邻索引值之间的 gap，会加一个 **Gap Lock**（退化自 next-key lock），锁住"user_id = :x 应该存在的那个间隙"

**效果**：别的事务执行 `INSERT INTO address(user_id, ...) VALUES(:x, ...)` 会被阻塞，直到本事务提交或回滚。也就是"0 条也能锁"。

#### 2. `user_id` 是唯一索引（或主键）

- **等值命中**：只加 **X record lock**，无 gap
- **等值未命中（0 行）**：**退化为 Gap Lock**，锁住相邻唯一值之间的间隙，同样阻止插入该 user_id

所以唯一索引下 0 行也能挡住插入，只是锁的是间隙而不是行。

#### 3. `user_id` 上没有任何索引

走全表扫描（聚簇索引全扫），RR 下会对**扫描过的每一条聚簇索引记录加 next-key lock**，实质等于把整张表的所有记录和间隙都锁了——其他事务对任何地址的插入都会被阻塞。

这不是"精准锁该用户"，而是"顺手把全表锁了"，属于并发灾难，但确实"0 条也锁"。

#### 4. RC 隔离级别（对照）

RC 下没有 gap lock（除非外键 / 唯一约束冲突），`WHERE user_id = :x` 未命中时就**什么都不锁**，0 行就是 0 行，别的事务可以立刻插入该用户地址。所以"0 条也能锁"这个特性是 **RR 专属**。

### 一个容易踩的坑

如果 `user_id` 是**联合索引的前缀**但不是单列索引，或者查询里带了别的条件下推，实际扫描的索引范围可能比你以为的大，gap 锁范围也会更大。具体以 `EXPLAIN` 的 `key` 和 `performance_schema.data_locks` 里看到的 `lock_data`、`gap` 为准。

## 方案二：Redis + MySQL（工业级标准，适合超高并发）

### 问题

- 同一 user_id 的 N 个并发请求
- 全部阻塞在同一个 user_id 的 Gap / 行锁上
- TPS 被压到串行级别
- RT 飙升
- 连接池打满
- 雪崩

### 1. Redis Key 设计

```text
addr:count:{user_id}
```

### 2. 新增地址流程（Lua 原子脚本）

**"原子状态机"**：

```lua
-- KEYS[1] = addr:count:{user_id}

local cnt = redis.call("GET", KEYS[1])
if not cnt then
    cnt = 0
end

if tonumber(cnt) >= 20 then
    return 0  -- 已达上限
end

redis.call("INCR", KEYS[1])
return 1  -- 允许插入
```

- ✅ **整个判断 + 计数是一个原子操作**
- ✅ **无锁**
- ✅ **QPS 可达 10w+**

### 3. 应用逻辑

```java
boolean allowed = redisTemplate.execute(luaScript, "addr:count:1001");
if (!allowed) {
    throw new AddressLimitException();
}

try {
    insertIntoMySQL(user_id, address);
} catch (Exception e) {
    // 回滚 Redis
    redisTemplate.decr("addr:count:1001");
    throw e;
}
```

### 4. 物理删除时

```sql
DELETE FROM address WHERE id = ? AND user_id = ?;
```

```text
DECR addr:count:{user_id}
```

- ✅ 名额立即释放
- ✅ 新地址可继续新增

### MySQL 的角色降级为"存储引擎"

MySQL 侧**不再负责限流**，只负责：

- 持久化
- 唯一性兜底（可选）

#### 表结构

```sql
CREATE TABLE address (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    user_id BIGINT NOT NULL,
    address VARCHAR(255),
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
    INDEX idx_user (user_id)
);
```

#### 插入

```sql
INSERT INTO address (user_id, address)
VALUES (?, ?);
```

#### 删除

```sql
DELETE FROM address
WHERE id = ? AND user_id = ?;
```

- ✅ 无唯一索引限制
- ✅ 无事务串行化
- ✅ 可水平扩展

### 异常处理（生产级必须）

#### 1. MySQL 插入失败

```java
if (mysqlInsertFailed) {
    redis.decr(key); // 回滚计数
}
```

#### 2. Redis 宕机降级（可选）

- 临时拒绝写入
- 或切换到 **DB + FOR UPDATE 降级模式**
- 事后对账修复

### 对账 & 修复（运维必备）

定时任务（分钟级）：

SELECT user_id, COUNT(*) AS real_cnt
